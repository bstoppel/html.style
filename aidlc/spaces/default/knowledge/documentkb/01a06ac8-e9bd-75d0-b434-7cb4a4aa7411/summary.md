Project guidelines for html.style, a modern web-standards CSS framework that is also a component library, starter template, design system and CSS methodology. Core philosophy: modern standards with no polyfills, AI-friendly machine-readable architecture, semantic HTML mapping to browser APIs, delete-key friendliness. Names AI agents as the primary users, which is why machine-readability drives every decision.

Browser support is stated as hard floors — Chrome/Edge 131+, Firefox 133+, Safari 18+ — set by FULL relative-color-syntax support, which the derived state tokens depend on (first support lands earlier but is partial). The file explicitly forbids restating the floor as a rolling version count, because engine cadences differ and Safari's numbering jumped 18 to 26 in 2025. It also records that the component APIs (Declarative Shadow DOM, ElementInternals, form-associated custom elements) all landed well below this floor, so the component layer requires no floor change.

Colours are OKLCH throughout. Cascade layers use the fixed order reset, tokens, atoms, molecules, organisms, templates. Tokens are three-tier: primitives (--p-*), semantic (--color-*, --space-*), and state derived via relative color syntax.

THE ARCHITECTURE IS MID-PIVOT TOWARD WEB COMPONENTS, and the atomic-design section is the load-bearing part. Three kinds of thing, and choosing between them is the first decision: atoms are semantic HTML elements with no classes and no components (style <button>, not .btn), carrying zero JavaScript and inheriting form participation, label association and default accessibility from the platform — the file explicitly forbids wrapping them to get an attribute API. Layout primitives (.stack, .cluster, .grid, .center, .switcher) are CSS classes, pure arrangement, also zero JavaScript, and explicitly not components. Molecules and organisms are web components prefixed hs-.

Components choose light or shadow DOM by one criterion — does it own structure, or arrange content? Light DOM when the component arranges consumer-provided content (hs-card, hs-alert, hs-hero): the global stylesheet keeps applying, slotted content flows, labels and forms behave, SSR is free. Shadow DOM when it owns internal structure the consumer should not restructure (hs-tabs, hs-dialog, hs-combobox). When in doubt, light DOM.

JavaScript policy is a boundary rather than a prohibition: none in atoms or layout primitives, expected in components. Progressive enhancement is explicitly SCOPED — atoms and layout work with JS disabled, components do not, since Declarative Shadow DOM renders markup but not interactivity, and the file forbids claiming otherwise in documentation.

Component conventions: hs- prefix, one element per file in src/components/, Lit for shadow components (the single sanctioned runtime dependency), DSD required, custom properties and ::part() as the public theming API (both breaking-change surfaces), a custom-elements.json manifest for tooling, and documented per-framework friction (Vue isCustomElement, Angular CUSTOM_ELEMENTS_SCHEMA, React 19+). Build-time partials under src/partials/ are a separate mechanism for the project's own pages, not part of the shipped library.

Accessibility: :focus-visible, WCAG AA contrast, prefers-reduced-motion, semantic landmarks, plus shadow-DOM specifics — <label for> does not cross the boundary, so use form-associated custom elements and ElementInternals. Core Web Vitals targets are LCP < 2.5s, CLS < 0.1, INP < 200ms.

CSS organisation: the global stylesheet is src/css/html.style.css (dist/ is generated from it), kept as a single file; shadow-component styles live with their component. The Do NOT list forbids BEM child classes, utility-first CSS, JavaScript for what CSS or semantic HTML handles, wrapping a working semantic element in a component, and appearance-based token names.

Closes with git workflow: Conventional Commits, hyphenated branch names, and a pre-commit checklist.
